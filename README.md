# Задача 2

## 📊 Вовлечённость в контент (Engagement Rate, ER)

**Вовлечённость в контент (Engagement Rate, ER)** - это процент уникальных пользователей, увидевших контент и совершивших с ним хотя бы одно целевое взаимодействие.

### Формула

```text
ER = (Uₑ / R) × 100%
```

Где:

* `Uₑ` - количество **уникальных пользователей**, совершивших хотя бы одно взаимодействие с контентом: лайк, комментарий, репост или сохранение.
* `R` - количество **уникальных пользователей**, увидевших контент (охват).

> Один пользователь учитывается в `Uₑ` только **один раз**, даже если он совершил несколько разных действий.

### Corner cases

1. **`R = 0`** - показатель `ER` не рассчитывается и получает значение `N/A`, чтобы избежать деления на ноль.
2. **Несколько действий одного пользователя** - пользователь считается только один раз в `Uₑ`.
3. **Отсутствуют данные** об охвате или взаимодействиях - `ER = N/A`, а не `0`.

### 📖 Термин для глоссария

**Уникальный пользователь** - пользователь, который учитывается в метрике только один раз, даже если он несколько раз просмотрел контент или совершил несколько взаимодействий с ним.

# Задача 3

### 1. Возможные гипотезы

**Гипотеза 1 - произошла склейка профилей пользователей (Identity Stitching).**
Ночью система могла провести дедупликацию пользователей: несколько анонимных устройств или cookie были связаны с одним авторизованным пользователем. В результате несколько ранее отдельных пользователей объединились в одного, поэтому итоговый охват уменьшился.

**Гипотеза 2 - сбился счётчик.**
Мог произойти технический сбой при загрузке или обновлении данных. Например, часть данных могла не загрузиться, обнулиться или быть потеряна, из-за чего исторический охват уменьшился.

**Гипотеза 3 - боты были удалены из данных.**
Система могла позднее обнаружить и исключить ботов или подозрительные аккаунты. Поэтому пользователи, которые вчера входили в охват, сегодня перестали учитываться.

**Гипотеза 4 - произошёл пересчёт исторических данных.**
Источник данных мог прислать исправления или могла измениться логика расчёта метрики. После повторного расчёта за тот же период система получила другое значение охвата.

### 2. Проверка одной гипотезы

Я бы проверил **гипотезу о склейке профилей пользователей**.

Сначала сравнил бы количество уникальных пользователей за нужный период до и после ночного обновления. Затем проверил бы историю склейки профилей и определил, появились ли связи между несколькими анонимными идентификаторами и одним авторизованным пользователем.

После этого проверил бы несколько конкретных примеров таких объединений. Если несколько ранее разных пользователей действительно стали определяться как один пользователь, а количество уникальных пользователей уменьшилось примерно на величину расхождения, гипотеза подтверждается.

### 3. Автоматическая проверка

Можно добавить автоматический контроль изменения исторического охвата после ночного обновления.

Система каждый день сравнивает новое значение охвата с предыдущей версией данных. Если показатель за уже завершённый период изменился более чем на **5%**, автоматически создаётся предупреждение:

```text
ALERT:
Охват за период изменился с 12 000 до 9 800 (-18,3%).
Необходимо проверить склейку профилей, удаление ботов и пересчёт исторических данных.
```

Такая проверка позволит обнаружить существенное изменение исторической метрики раньше, чем его заметит бизнес-заказчик.
